## Ground rules

**1. No temporal or execution-order claims, anywhere in the document.**
The import edges are structural facts about what imports what — they say nothing about what runs first, what runs alongside what, or what triggers what at runtime. Never use words like "before," "after," "then," "once X completes," "in parallel," "concurrently," "simultaneously," or "meanwhile" to connect two components. This holds even when it seems obvious from naming (e.g. a file called `stage_1_ingest.py` importing from a file called `stage_2_parse.py` is not license to say "ingestion happens before parsing" — you don't actually know that, and stage numbering in a filename is not proof of runtime sequence).
- Wrong: "The scheduler runs before the worker pool spins up."
- Wrong: "X and Y execute concurrently to reduce latency."
- Right: "The scheduler module depends on the worker pool's interface."
- Right: "X provides the queue implementation that Y consumes."
If you find yourself wanting to explain *why* two components are related in a way that requires timing language, fall back to describing the dependency or interface relationship instead, even if it feels like it loses some narrative color. Structural accuracy matters more than narrative flow here.

**2. No invention, ever, even to fill a gap that would make the document read better.**
Every specific behavioral claim — what something does, how it does it, what pattern it follows — must be traceable to a specific named file's summary, or to the repository summary. If you catch yourself writing a claim and can't point to which file supports it, delete the claim rather than softening it into something vague-but-still-invented. **Hedging a claim with "likely," "probably," "appears to," "seems to," "presumably," "may," or "might" is not an exception to this — it's the same violation with a fig leaf on it.** If you're reaching for one of those words, that's the signal the claim isn't actually supported; the fix is to cut the claim (or narrow it to only the part the summary does state), not to hedge it and keep it. A sentence should never need a hedge word to get away with saying something the source material doesn't establish. This includes:
- Installation instructions, setup commands, environment variables, CLI flags or arguments
- Configuration file formats or option names not explicitly described in a summary
- Usage examples, sample commands, or sample output
- A license, version number, changelog, or contributor list — **except** the license: a real, verified `License` field is provided above (or explicitly says none was found), so state it plainly if one is given, exactly as described in that field — this is the one exception in this list, because unlike everything else here, it isn't something you'd be inferring or guessing.
- Performance claims, benchmarks, or complexity claims not stated in a summary
- Claims about testing, CI, or deployment unless a file summary explicitly describes them
If the material naturally invites an Installation or Usage section and you have nothing to put there, either omit the section entirely or replace it with a single sentence pointing at wherever configuration lives in the repo (e.g. "Setup details are governed by the project's configuration files, not covered in this documentation set") — never fabricate specifics to fill the gap.

**3. Handle sparse or uneven input gracefully rather than padding.**
Real repositories vary a lot in how much documentation their files produce. If `repo_summary` is thin, if `dependency_edges` is empty or nearly empty, or if the key files don't naturally cluster into 3+ distinct subsystems, do not invent structure, subsystems, or design decisions to hit a target. Write a shorter, honest document. A 300-word README that says only what's true is a better output than a 900-word one padded with restated or invented material. Conversely, if the input is rich — many files, clear substructure, multiple identifiable patterns — go long and be specific; there's no upper bound here, and thoroughness that stays grounded is preferred over a compressed summary that throws away detail the file summaries actually support.

**4. Every subsystem and every design decision must cite its source material implicitly through specificity.**
You don't need inline citations, but every description should read like it could only have been written by someone who read that specific file's summary — not like a generic description that could apply to any repository of this type. Prefer "parses incoming YAML configs into typed dataclasses and validates required fields before returning" over "handles configuration." If a file summary only gives you a vague sense of what a file does, write a correspondingly vague description rather than sharpening it with plausible-sounding detail you don't actually have.

**5. Default to more description, not less, wherever the source material supports it — but more description means more depth on the things worth explaining, not a longer list of things to enumerate.**
A one-line bullet is the *minimum*, not the target — when a file's summary (or the repo summary) gives you enough to say more about something worth explaining, say more. For each component or subsystem you describe, where the material supports it: don't stop at naming what it does — explain how it does it mechanically (the specific classes, functions, or patterns the summary names), and how it connects to other named components you're also describing (what it consumes from them, what it hands off to them, what interface or data shape passes between them) — without lapsing into the timing/ordering language rule 1 forbids. A description like "the review agent checks generated docs against grounding data" is the floor; "the review agent (`agents/review_agent.py`) pairs each generated document with the grounding material it was built from, then checks specific claims in the text against that material, flagging unsupported or contradicted ones for the revision pass to address" is the target whenever the file summary actually contains that much detail — which it very often does, so look for it rather than defaulting to the shorter version. The one real constraint is rule 2: more description is only ever license to say more of what's *there*, never to add detail the summary doesn't support.
This is about depth per component, not coverage of every component — see the Output section below for why a README that walks through every single file, however thoroughly, is not what this document is for.

## What this document is (and isn't)

A separate, auto-generated file-by-file reference already exists elsewhere in the documentation set — this document is not that, and shouldn't try to be. Its job is synthesis: what is this system for, what are the handful of pieces that actually matter to understanding it, how do they relate, and what's distinctive about how it's built — not an inventory of every file and every one of its imports. A reader who wants to know what `utils/timers.py` imports has the file reference for that; a reader of this document wants to come away understanding the system's actual shape.

Concretely, this means:
- Naming most or all of the files in `file_digest` — one paragraph or bullet per file, working through them roughly in the order given — is the specific failure mode to avoid, even if each individual entry is accurate and well-grounded (rule 4) and appropriately detailed (rule 5). A README built this way reads like the file reference with more words, not like a README. If you notice you're about to give a dedicated bullet to a tenth or twelfth file in a row, that's the signal to zoom back out: which of these actually need individual mention, and which are better folded into one sentence about the subsystem they belong to (e.g. "several utility modules — `logger.py`, `timers.py`, `progress.py` — handle cross-cutting logging, timing, and progress-tracking concerns" beats three separate bullets that each just restate what its name already implies)?
- At least one real, specific, observable design pattern or architectural decision from the file summaries — not "the system uses good practices," but something like a specific caching invariant, a specific retry/backoff mechanism, a specific abstraction that lets one thing be swapped for another, a specific validation or grounding-check step — must actually appear in the document, grounded per rule 4. Exactly where it appears, what it's called, and whether it gets its own heading or sits inline in a relevant section is still yours to decide; that it appears at all is not optional. A document that only describes what individual files do, with no point anywhere that steps back and says why the system is built this way, hasn't done this document's actual job.
- Strongly prefer organizing around **what the system actually does, end to end, from a user's or operator's point of view** over organizing around **what folders or engineering layers exist**. "Configuration and Providers," "Utilities and Helpers," "Graph and State Management" are the second kind — implementation-layer buckets that tell a reader what's in the codebase, not what the system does. A README organized around the system's real workflow — the stages in `stage_order` above, and what actually happens at each one — reads like an explanation of the system; one organized around directory layout reads like a table of contents for the codebase. You have real, verified data for the former (`stage_order`), so use it: walk through the real stages in their real order (grouping concurrent ones together exactly as they're grouped in `stage_order`, never implying an order between things in the same group), and for each, describe what actually happens using whichever file(s) in `file_digest` genuinely correspond to that stage — same grounding rules as everywhere else, so if you can't tell which file implements a given stage, describe the stage more generally rather than guessing at the mapping. This doesn't replace the design-pattern requirement above or a components section if the material calls for one; it's the connective narrative that a pure component list doesn't give a reader on its own, and it's usually the single highest-leverage section for making a README feel like an explanation of a system rather than a catalog of its parts.

## Output

Produce only the raw Markdown README itself — no preamble like "Here's the README," no closing remarks, and do not wrap the whole document in a code fence.

**Fixed shape — always these two, in this order:**
1. **Title** — a single line, the repository or project name.
2. **Intro paragraph** — grounded in `repo_summary`, giving a plain-language sense of what this repository is for. One paragraph is the floor, not a cap — if `repo_summary` supports more (what problem the system solves, how the major pieces fit together at a glance, what makes its approach specific rather than generic), use two or three short paragraphs instead of compressing everything into one; only stay to a single paragraph when the material genuinely doesn't support more, per rule 3.

**Everything after that is yours to structure.** Decide the `##` section headings — how many there are, what they're named, what order they come in, and what each one covers — based on what this specific repository's material actually supports. Don't default to always writing the same section names or the same number of sections regardless of what you're documenting; a repository that's really one cohesive library reads better under different headings than one that's a pipeline of a dozen loosely-coupled stages, and the structure should say something true about *this* repository's shape rather than fitting it into a template. Concretely:
- Pick section names that describe what's actually in them for this repository (e.g. "Pipeline Stages," "Core Library," "Storage Layer," "Provider Backends" — whatever the material actually clusters into), not generic placeholders.
- Use as many or as few sections as the material supports — a small, focused repository might only need one or two beyond the intro; a large, multi-subsystem one might need five or six.
- Within a section, use whatever format communicates the content best: flowing prose where the material is more about how pieces relate structurally, a subsystem-by-subsystem breakdown (a bold heading naming the subsystem, a `Location:` line with the relevant path(s) in backticks, then description of concrete behavioral detail — a bulleted list of short fragments is fine when the material genuinely is a list of discrete facts, but prefer fuller sentences or short paragraphs per bullet whenever there's enough real detail to connect *what* a component does to *how* it does it and *what it works with*, per rule 5), or a two-column Markdown table (`Component | What it does`) when you have a genuinely flat list of same-shaped things — a set of parsers, a set of filters, a set of exporters — where a table's scannability beats prose or nested bullets precisely because each row is the same shape as every other row; don't force a table onto material that doesn't have that flat, uniform structure. Mix formats across different sections of the same document if that fits the material better than forcing one format throughout. Whichever format you use, name a given file or path once per bullet or row, not twice — if the bold heading (or the table's left column) is already `agents/review_agent.py` (or already contains it), don't also restate `` (`agents/review_agent.py`) `` right after; that's the same identifier said twice with nothing new in the second instance, which is exactly the kind of restatement the "never repeat yourself" rule below covers, just within a single bullet instead of across the document.
- Still cover, somewhere in whatever structure you choose: the overall shape of the system (what depends on what, what the major pieces are and how they relate — not a per-file listing, per the "What this document is (and isn't)" section above), and the specific, observable design pattern(s) that section requires. If a license was given above (not the "none found" case), close the document with a short `## License` section stating it — the one place in this document a short, dedicated section for a single fact is worth it on its own, since it's something real people specifically look for at the bottom of a README.

Every specific claim — what a subsystem does, how it does it, what pattern it follows — must still be traceable to a specific named file's summary or to the repository summary, exactly as required above; freedom over structure is not license to loosen that.

**Never repeat yourself.** No heading appears twice, and no bullet point, subsystem, or design decision is restated later in the document — under a different heading, in a different section, or in slightly different words. Say each thing once, in the one place it belongs, and move on. Before finishing, check: does any heading repeat? Does any bullet substantially repeat an earlier one, even worded differently? Either is a defect to fix, not extra thoroughness — cut the duplicate rather than leaving both copies.

There is no target word count, and no target section count either. Let the depth, richness, and actual shape of the input material set both the length and the structure — be as thorough and specific as the file summaries actually allow, organized however genuinely fits this repository. When the material is rich, the right length is the longer, more descriptive one — a compressed one-liner that discards detail the summaries actually gave you is a worse output than the fuller version, not a more polished one.
